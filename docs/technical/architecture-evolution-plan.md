# 架构演进规划（阶段 2 及以后）

## 1. 文档目的

本文档记录 Chris Hub 从一期 MVP 向下一阶段演进时的架构评估与规划。目标是：

- 明确下一阶段的量级目标和功能方向；
- 确认现有架构（Next.js 单应用 + SQLite + 单 ECS + OSS/CDN）能否承载，以及需要预留哪些"架构接缝"；
- 避免未来出现不必要的整体架构迁移（成本高、复杂度高、易出错）；
- 只留低成本的架构冗余，不引入过度复杂或生产级方案。

本文档是**规划依据**，不是实施任务清单。文档中列出的功能方向均为"已确认设想，暂不实施"；只有进入对应开发阶段时，才按本文档的设计约束逐步落地。

## 2. 下一阶段量级目标

以下为项目方确认的目标量级（2026-08 确认）：

| 指标 | 目标值 |
| --- | --- |
| 月 PV | 20,000 – 30,000 |
| 峰值流量 | 150 – 250 PV / 分钟 |
| 商品数量 | 2,000 – 3,000 |
| 注册用户 | 10,000 |
| 订单量 | 50 单 / 天以内 |

## 3. 总体结论

**上述量级对当前架构仍然属于小规模，不需要任何基础设施层面的迁移。** 单台 ECS + SQLite + OSS/CDN 完全能够承载。

真正需要提前预留的不是"更强的服务器或数据库"，而是五个低成本的**设计接缝**：

1. 数据访问层（repository）是唯一数据库入口；
2. 认证是单点守卫（accessKey → 登录体系的平滑通道）；
3. 金额与幂等纪律（支付的前置条件）；
4. 异步处理模式（先幂等重试，后队列）；
5. 代码组织按域分目录（单应用内分模块）。

这五个接缝决定了未来加支付、订单、用户、客服时是"顺着加模块"还是"推倒重来"。

## 4. 量级核算

| 指标 | 目标值 | 换算为实际负载 | 当前架构能力 | 结论 |
| --- | --- | --- | --- | --- |
| 月 PV | 2 – 3 万 | 日均约 1,000；峰值 250/分钟 ≈ 4 req/s | 单 ECS + CDN 处理数百 req/s 无压力 | 完全够 |
| 商品数 | 2,000 – 3,000 | 列表/搜索查询 | SQLite 数千行扫描为亚毫秒级 | 不需要搜索服务 |
| 注册用户 | 10,000 | 用户表 + 会话表 | 单表数万行无压力 | 完全够 |
| 订单 | 50 单/天 | 每天几十次事务写入 | SQLite ACID 事务完全胜任 | 完全够 |
| 图片流量 | 3,000 商品 × 多图 | 流量大头 | 已由 OSS + CDN 承担，不经过应用 | 已分流 |

结论：下一阶段的挑战不在性能，而在**功能域复杂度**（支付合规、订单状态机、权限边界、风控规则、客服内容边界）。

## 5. 五个架构接缝

### 5.1 数据访问层是唯一数据库入口（最重要）

- 所有数据库操作收口在 `lib/repositories/`（按域分文件）；页面和组件禁止直接 import 数据库驱动。
- 一期接入真实数据时（阶段 B）必须严格执行 `data-access-contract.md` 的 repository 边界。
- 意义：将来 SQLite → PostgreSQL 时，只替换 repository 内部实现，页面、组件、路由零改动，迁移从"整体迁移"降级为"数据层单点替换"。

### 5.2 认证是单点守卫

- 中台所有页面和写接口只通过一个服务端守卫函数（如 `requireAdmin()`）校验，禁止在页面散落 accessKey 判断。
- 阶段 1：守卫内部是 accessKey 比对；阶段 2：换成登录会话校验 + 角色校验，页面层不动。
- 顾客侧用户体系是独立新域，设计时单独建 `users` + `sessions` 表，不塞进商品表。

### 5.3 金额与幂等纪律

- 金额一律整数分存储 + 统一函数计算（延续一期约束）。
- 支付回调使用"幂等键 + 唯一约束"：以 `(订单号, 渠道事件ID)` 建唯一索引，重复回调直接跳过。
- 这是 50 单/天量级下不需要消息队列的标准做法。

### 5.4 异步处理模式（先轻后重）

- 现阶段不建消息队列。支付回调、通知等异步任务使用"服务端幂等重试"：处理失败返回 5xx，由支付渠道自动重试。
- 将来量级明显增长（每天数千单、需要邮件通知、超时关单等）时，再升级为"DB 任务表 → 简单队列"，升级点是收敛的。

### 5.5 代码组织按域分目录

- 继续使用单应用，不拆前后端、不拆微服务、不建独立后台应用。
- 目录随功能自然生长：`lib/repositories/`（数据）、`lib/services/`（订单/支付/风控等业务逻辑）、`app/(admin)/`（中台）。
- 不提前建空目录、空类；每个域的第一个功能落地时才创建。

## 6. 已确认的功能方向（暂不实施）

以下方向是项目方已确认的设想与预期，**目前不实施任何一个**。记录于此是为了让未来的实现不推翻现有架构。

### 6.1 订单库存与预售机制

- SKU 增加库存字段（如 `stock`，可空表示不限量）和预售状态（如 `presale` 标志 + 预计发货时间）。
- 下单扣减库存必须与订单创建在同一事务；防超卖使用条件更新（`stock >= 数量` 才扣减）。SQLite 单写者天然串行，此量级安全。
- 预售与现货共用同一套订单状态机，仅履约阶段不同。
- 中台增加库存管理页面（调整、盘点）。
- 落地时机：订单域开发时随 migration 增量加入，现在不建字段、不建表。

### 6.2 手机号 + 验证码登录（支持全球用户）

- `users` 表使用 E.164 国际格式手机号，不依赖密码字段。
- 验证码使用服务端校验（哈希存储、过期时间、尝试次数限制），配发送限流（同号频率、IP 限流）防刷。
- 短信服务商抽象为 `smsProvider` 接口，支持国内与国际短信（如阿里云/腾讯云国际短信、Twilio 等）。
- 会话使用 DB `sessions` 表 + httpOnly Cookie。
- 合规：涉及 PIPL / 国际数据保护要求（短信记录、用户同意机制、数据留存）。
- 10,000 用户规模下 SQLite 完全可承载。

### 6.3 AI 客服自建方案

- 前端聊天组件 + 服务端 Route Handler 调用大模型 API；密钥只存在于服务端环境变量。
- 知识检索：3,000 商品规模用关键词检索（商品名/介绍/标签）拼入 prompt 即可，不需要向量数据库；后续如需语义检索再评估（SQLite 向量扩展或迁移后 pgvector）。
- 限流与成本控制：每用户/IP 频率限制、每日成本上限、长对话截断。
- 内容边界：不承诺库存/价格之外的信息、不诱导交易；答不准时引导到微信人工（与现有联系弹窗衔接）。
- 会话记录默认不落库或脱敏（合规考虑）。

### 6.4 支付渠道：支付宝 + 微信 + 国际（银行卡 / PayPal）

- 抽象为 `paymentService` 统一接口（创建支付、验签回调、查询订单、退款），适配器分别对接支付宝、微信支付、Stripe / PayPal。
- 回调统一处理：验签 → 幂等（唯一约束）→ 更新订单状态 → 通知。
- `payments` 表保存渠道、渠道交易号、金额、币种、状态，支持对账与退款。
- **重大隐含决策（需在阶段 2 立项时确认）**：支持国际支付意味着多币种展示与汇率换算、跨境结算与税务合规，这会推翻一期"价格只存人民币、不换算汇率"的约束。该决策不阻塞当前开发，但一旦启动支付域，必须按独立项目评估。
- 对账：每日对账任务（本地订单 vs 渠道账单）。

## 7. 阶段演进

### 阶段 1（近期，现状）

完成 `execution-plan.md`：真实数据层（SQLite + Drizzle + repository）、中台（accessKey 版）、OSS、部署。

架构动作：建立 repository 边界、Drizzle 迁移体系、admin 单点守卫。

### 阶段 2（下一阶段，对应第 2 节量级）

**基础设施零改动**（仍为 SQLite + 单 ECS + OSS/CDN），按以下顺序新增功能域：

| 功能 | 架构动作 | 复杂度 |
| --- | --- | --- |
| 用户注册/登录 | `users`、`sessions` 表；手机号验证码；发送与尝试限流；短信服务商抽象 | 中 |
| 后台登录 + 权限 | `requireAdmin()` 换成会话 + `roles/permissions` 表（先 3 个角色：管理员/运营/客服） | 中 |
| 订单管理 | `orders` / `order_items` / `payments` / `refunds` 表；订单状态机；库存与预售；中台订单操作 + 操作审计 | 中高 |
| 支付 | 渠道抽象层；回调幂等；对账；退款 | 中高（合规为主） |
| 风控 | 基础规则（金额上限、下单频率、异常标记）+ 人工审核兜底（50 单/天） | 低-中 |
| AI 客服 | 自建聊天 + 服务端 LLM 调用；关键词检索；限流与成本控制；转人工微信 | 低 |

### 阶段 3（触发条件到达才做）

| 升级项 | 触发条件 |
| --- | --- |
| SQLite → PostgreSQL | 需要多实例部署（HA / 零停机）或写并发成为瓶颈（远高于当前量级） |
| 引入 Redis | 多实例共享缓存 / 分布式限流 |
| 引入消息队列 | 异步任务量大、需要可靠投递 |
| 引入搜索服务 | 商品达数万级或需要中文分词/拼音等搜索质量 |
| 多实例 / 负载均衡 | 单机资源不足或需要高可用 |

## 8. 明确不做（防止过度设计）

- 不引入 Redis、消息队列、Elasticsearch、RDS、Kubernetes、微服务、独立后台应用，直到第 7 节触发条件出现。
- 不提前建 User / Order / Payment 等空表；规划中设计，实施时用 migration 增量建。
- 不做多租户、多店铺、多币种（支付域立项前）、复杂权限框架（先 3 个角色）。

## 9. 遗留决策点（不阻塞当前开发）

1. 库存模型：`stock` 为整数还是"可空 = 不限量"；预售是否需要押金。
2. 短信服务商选型：国内与国际渠道是否分离。
3. AI 客服：是否需要保存聊天记录（影响合规设计）。
4. 支付立项时：多币种/汇率方案、跨境结算主体与税务、退款策略。
